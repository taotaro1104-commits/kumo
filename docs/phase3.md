# Phase 3：メモリ管理（MemoryGovernor・Frozen / Discarded・OS メモリ圧迫・about:memory）

設計書ロードマップ Phase 3。完了条件：設計書のメモリ目標をすべて達成する。

## タブの状態

| 状態 | 保持するもの | 捨てるもの | 戻すとき |
|---|---|---|---|
| Live | すべて | なし | — |
| Frozen | DOM・スタイルシート・題名・スクロール位置 | スクリプト（Boa のヒープ）・描画命令・レイアウト | 表示するとき再レイアウトのみ（取得し直さない）。スクリプトは戻らず、静的な文書として表示する |
| Discarded | URL・題名・履歴・スクロール位置（Browser 側） | ページを丸ごと | 表示するとき URL を読み込み直し、読み込み後にスクロール位置を戻す |

- 表示中のタブと読み込み中のタブは降格しない。
- 入力中の欄がある・POST で開いたページは凍結まで（破棄すると失うため）。
- 破棄したタブは Content にもページが残らない。タブ見出しは薄い文字と ○ で示す。

## MemoryGovernor（`kumo-browser` の `governor.rs` と `memory.rs`）

判断は純粋な関数 `plan(policy, tabs, used, pressure)`、実行は `Browser::govern`。ウィンドウは 2 秒ごとに
`maintain_memory` を呼び、Content のメモリ（`Stats`）・Browser 自身のメモリ・OS の圧迫から降格を決める。

| 条件 | 動作 |
|---|---|
| 背景に回って 60 秒 | 凍結 |
| 最後に見てから 15 分 | 破棄（凍結済みでも、凍結を飛ばしても） |
| Browser + Content が予算（既定 200MB）を超える、または OS の圧迫が中 | 背景の Live を古い順にすべて凍結。凍結しかなければ古い順に 1 枚だけ破棄（測り直してから次を判断） |
| OS の圧迫が危険 | 背景のタブをすべて破棄（保護されたものは凍結） |

## OS のメモリ圧迫（`kumo-mem` の `pressure.rs`）

空き物理メモリの割合で判定する：15% 未満＝中、7% 未満＝危険。Windows は `GlobalMemoryStatusEx`、
Linux は `/proc/meminfo` の `MemAvailable`。設計書の `QueryMemoryResourceNotification`・PSI は通知型だが、
ここでは 2 秒ごとの確認で同じ段階を得る（通知型への置き換えは判定関数 `classify` を変えずに可能）。

## about:memory

URL 欄に `about:memory`。Browser・Content の使用量、予算、OS の圧迫、方針、降格の累計、
各タブの状態（live / frozen / discarded）と最後に見てからの時間を出す。開いた時点の値で、再読み込みで更新する。

## 引数

`--memory-budget MB`、`--freeze-after 秒`、`--discard-after 秒`。ヘッドレス（`--headless`）では、
指定した時間が経ったことにして背景のタブを降格してから計測する（`--mem-report` と組み合わせて凍結・破棄後のメモリを測れる）。

## 見つけて直した問題：Boa のヒープが返らない

ページを閉じても Boa のオブジェクトは回収されず、メモリが残っていた（JS ページ 8 枚を作って捨てても 48MB → 46MB）。
`boa_gc::force_collect()` を呼ぶと 3MB まで戻る。`JsRuntime::shutdown` で文脈を捨ててから回収し、
`Page` の破棄・凍結で必ず呼ぶ。同様に、取得スレッドで確保した DOM を別スレッドで捨てても確保元が回収するまで
OS に返らないので、降格のたびに取得スレッドへ回収の仕事（`Work::Trim`）を送る。
この修正は通常のページ遷移・タブを閉じる場合にも効く。

## 計測（リリース、Windows 11、3 プロセス合計）

| シナリオ | 結果 | 目標 |
|---|---|---|
| 空白タブ | 22.0MB | 30MB |
| Wikipedia 1 タブ（JS あり） | 64.9MB | 70MB |
| 一般的なサイト 10 タブ（JS あり） | 179.1MB（Browser 8.3 + Content 131.9 + Network 38.9） | 250MB |
| 同・背景の 9 タブを凍結 | 125.6MB | — |
| 同・背景の 9 タブを破棄 | 117.0MB | — |

凍結したタブ 1 枚あたりの Content のメモリは、凍結した 9 タブの合計の増分（78.3MB − 破棄後の 68.4MB ÷ 9）で約 1MB。
Wikipedia 1 タブの場合の値（37MB）を床としても、凍結タブ 1 枚あたり 5MB を下回る（目標：5MB 以下）。

## 既知の制限

- 凍結から戻したページではスクリプトが動かない（タイマー・イベントは戻らない）。動的なアプリは破棄に近い扱い。
- 破棄から戻すと入力途中の欄の値は失われる（入力中の欄があるタブは破棄しないが、凍結は行う）。
- Network プロセスのメモリは予算の判断に含めない（Browser と Content のみ）。
- 圧迫の確認は 2 秒間隔のポーリング。
