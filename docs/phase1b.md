# Phase 1b：プロセス分離（Content プロセス・共有メモリ・非同期読み込み）

Phase 1 で残した簡略化のうち、構造に関わるものを設計書の形に近づける。

## 目標

1. **Content プロセス**：ページの処理（取得要求・パース・スタイル・レイアウト・ラスタライズ）を Browser プロセスから分離する。
   設計書の低メモリ時の形（Content プロセス1つに全タブ同居）から始め、タブ→プロセスの対応を持たせて後で N 個に増やせるようにする。
2. **非同期読み込み**：Browser は Content へ要求を送るだけで待たない。読み込み中も UI（タブ切替・スクロール・URL 入力）は動く。
3. **共有メモリ**：
   - 画素：Content が共有メモリのフレームに描き、Browser はウィンドウへ写すだけ（設計書「Browser がウィンドウに合成」）。
   - 本文：Network → クライアントの大きな本文は接続ごとの共有メモリのリングで渡す（入りきらなければパイプにフォールバック）。

## 構成

```
Browser ──stdin/stdout──▶ Content（全タブの Page、ScrollRenderer、共有フレームへ描画）
   │                         │
   └──local socket──▶ Network ◀──local socket──┘   （1つの Network を共有、接続ごとに本文リング）
```

- `kumo-ipc`（新規、unsafe はここと kumo-mem のみ）：ファイルを使った共有メモリ、リングの領域管理、ローカルソケット名。
- `kumo-net`：`--listen 名前` で複数クライアントを受け付ける。接続の最初に本文リングのパスを伝える。
- `kumo-content`（新規）：`ContentEngine`（要求→応答の純粋なロジック）と、プロセス／スレッドとして動かすホスト。
- `kumo-browser`：タブ・セッション履歴・閲覧履歴・UI。ページは持たず、Content からの通知で状態を更新する。
- テストと `--in-process` では Content をスレッドで動かす（同じ `ContentEngine` を使う）。

## 段階

1. `kumo-ipc`：共有メモリとリングの領域管理（単体テスト）
2. Network の複数クライアント化と本文リング（実プロセス間テスト）
3. `kumo-content`：エンジンとホスト（スレッド版でテスト）
4. `kumo-browser` をメッセージ駆動に作り替え（スレッド版 Content でテスト）
5. ビューア：Content プロセス起動、イベントループでの受信、共有フレームの合成
6. 計測：10 タブで 3 プロセス合計

## 実装

- **Network**：`--listen 名前` でローカルソケット（Windows は名前付きパイプ）を待ち受け、起動したら `ready` を出す。
  最初の接続（起動した Browser）が閉じたら終了。後から来た接続（Content）は同じ `NetworkService`（キャッシュ・Cookie・ブロック）を共有する。
  接続ごとに 4MB の本文リングを作り、最初に `Hello` で場所を知らせる。16KB 以上の本文はリングに置いて位置と長さだけを送り、
  受け手は複製したら `Release` で返す。リングが満杯ならメッセージに入れて送る（待たない）。
- **Content**：`ContentEngine` は入出力を持たないロジック（要求 → 通知、取得は `FetchJob` として外へ出す）。
  ホストは要求と取得結果を1つのキューで受け、溜まった分をまとめて処理してから1回描く（入力の連続は1回の再レイアウトになる）。
  取得とパースは常駐の取得スレッド、スタイル・レイアウト・描画はメインスレッド。読み込みには通し番号を付け、古い結果は捨てる。
  画像は取得スレッドで先に取得し、レイアウト中に取得で待たない。
- **フレーム**：Content は表示中のタブを共有メモリ（コンテンツ領域の大きさの 0RGB）に描き、`Frame` で描き直した行を知らせる。
  Browser はウィンドウへ写して `FrameDone` を返す。それまで Content は次を描かないので同時に触らない。スクロールは前のフレームをずらして帯だけ描く。
- **Browser**：タブ・セッション履歴・URL 欄・UI だけを持つ。移動・クリック・キー入力は要求として送り、`Loaded`・`Navigate`・`FieldFocus`・`Scrolled`・`Frame`
  の通知で状態を更新する。通知が届くとイベントループのユーザーイベントで起こされる。
  同じ文書内の `#id` への移動（戻る・進むを含む）は取得せずに `ScrollToFragment` を送る。
- テストと `--in-process` では Content をスレッドで動かす（同じエンジンとメッセージ）。

## 結果（2026-10-27）

リリースビルド、1280×900、Windows 11。値は3プロセスの private commit の合計（`--mem-report` の `[total]`）。
共有メモリ（フレーム・本文リング）はファイルのマップなので private commit には入らない。

| シナリオ | 結果 | 目標 |
|---|---|---|
| 空白タブ | 20.0MB（Browser 7.1 + Content 5.9 + Network 7.0） | 30MB |
| Wikipedia 1 タブ | 56.7MB（Browser 7.0 + Content 33.5 + Network 16.2） | 70MB |
| 一般的なサイト 10 タブ（Phase 1 と同じ） | 128.7MB（Browser 8.0 + Content 84.1 + Network 36.6） | 250MB |

- 同じ 10 タブを `--in-process` で動かすと 93MB（Phase 1 の 91MB と同程度）。差の約 35MB はプロセスごとの土台
  （アロケータ・フォントDB・スレッド）と、Network の接続が2本になった分。
- 取得スレッドを 2 本以上にすると 10 タブで約 12MB 増えた（スレッドごとのヒープに DOM が分かれる）ため 1 本にした。
  読み込みは順番になるが、UI と表示中のタブは止まらない。

## 精査で直した点

| 重要度 | 問題 | 修正 |
|---|---|---|
| 高 | 写していないフレームを捨てる場面（タブ切替・リサイズ・ヘッドレスの待機）で `FrameDone` を返さず、Content が次を描かなくなる（画面が固まる） | 捨てるときも必ず通知する（`discard_frame`） |
| 高 | 共有メモリのファイルが一時ディレクトリに残る（Windows はマップ中のファイルを消せず、異常終了では Drop も走らない） | Windows は「閉じたら消す」で作成し、全員が閉じた時点（強制終了を含む）で OS が消す |
| 高 | 相手から届いたパスを検査せず読み書きでマップ。名前が推測でき、既存ファイルを切り詰めて開く | 読み手は読み取り専用（`SharedView`）で、一時ディレクトリの `kumo-*.shm` だけを開く。作成は新規のみ（Unix は 0600）。ファイル名とソケット名に推測しにくい値を含める |
| 中 | Content が落ちると全タブが「読み込み中」のまま | Browser が検知して Content を作り直し、全タブを読み込み直す（上限3回）。作り直せなければ UI に表示する |
| 中 | 取得スレッドが1本のため、表示中のタブの移動が背景タブの読み込みの後ろで待つ。取り消された読み込みも取得する | 待ち行列で表示中のタブを先頭に回し、同じタブの古い依頼と閉じたタブの依頼は捨てる |

## 残る制限（Phase 2 で JS を追加した後も有効なもの）

- Content プロセスは1つ（全タブ同居）。タブ→プロセスの対応を持たせて N 個に増やすのは今後。
- タブの読み込みは1本ずつ順番（省メモリのため。表示中のタブは先に回す）。10 タブを一度に開くと、文書の取得待ちの合計
  （この環境で約 5 秒）がかかる。ページのパース・スタイル計算中は Content のメインスレッドが塞がるので、
  その間は表示中のタブのスクロールが一瞬遅れることがある（UI 自体は Browser が描くので止まらない）。
- `<select>` はクリックで次の選択肢へ送る簡易操作（ドロップダウンは未実装）。
- 入力欄をクリックした直後、フォーカスの通知が届く前に押したキーはページの操作（Space でスクロールなど）として扱われる。
- Unix では異常終了したプロセスの共有メモリのファイルが残りうる（正常終了では消す）。
- Content が作り直されたとき、フォームに入力途中の値とスクロール位置は失われる。
